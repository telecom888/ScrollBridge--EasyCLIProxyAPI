# Go beta 实现与现有项目对比

> 历史报告：对应首次独立核心交付（提交 85fc529 / Go beta 0.1.0）。后续桌面移植和验证见 DESKTOP-0.3.0.md；下列“尚未移植”与测量数据均描述当时版本。

测试时间：2026-10-21T03:50:44.398Z。分支：beta/go-gateway；Node 基线：main 的 2d198bf，桌面版 0.2.1。

## 判断

分层、全局与单 key 交集、消费凭证与供给凭证分离，是合理的网关设计方向；仅凭这些抽象，不能客观给出“85–90 分、已达企业级”的结论。还需要协议覆盖、故障恢复、资源上限、安全验证与运维证据。现有 Node 网关已经有路由白名单、协议解析约束、增量 SSE、WebSocket 撤权和本地密钥保护，不能简单称为玩具。

N:1 别名解决的是命名与授权解耦，本身不实现 A/B 或灰度；后者需要一对多候选、分流与调度。Python 异步 I/O 和 Java NIO/虚拟线程也能承载大量长连接，语言不能单独决定网关等级。io.Copy 与对象池也不等于网络零拷贝。选择 Go 的主要理由是标准网络库、取消传播、并发调试和单 exe 交付。

该 beta 证明了关键工程机制可落地，尚未证明具备完整生产平台能力。Redis Pub/Sub 的消息可能丢失；轮询可以限制配置陈旧时间，不能替代财务账本的强一致性。使用静态配置的单机桌面网关不需要被强行改成 Kubernetes + Redis 平台，Redis 在此仅为可选模式。

## 完成的实现

| 能力 | 现有 Node 网关 | Go beta |
|---|---|---|
| 多 key、全局优先、别名/原始 ID | 有，桌面配置 | 有，配置编译成索引与不可变快照；别名独立授权 ID |
| 配置更新 | 主进程提交后热更新 | 版本校验、原子替换；全部旧请求取消；配置失联 5 秒后阻断 |
| SSE | 增量转发，别名事件有限额 | 增量事件、同步背压、输出总量与写超时、取消传播 |
| 资源管理 | 64 活动请求、单请求限额 | 全局/单 key 并发、TCP 连接上限、共享缓冲预算、读写时限 |
| 供给入口 | 一个本地代理 | 可选多个等价入口，最少活动数、429/5xx 冷却、半开探测 |
| 自动重试 | 无 | 生成请求不自动重试；下一新请求可选健康入口 |
| 多节点配置 | 无需此能力 | 可选 Redis 持久版本 + 通知 + 500 ms 轮询 |
| 额度 | 无 | 本地 fsync 预留账本或 Redis 原子预留；中断保守记账 |
| 费用 | 无 | 输入/输出/缓存命中手动费率；读取 usage 费用开关；节点本地审计 |
| WebSocket、图像 edits、Gemini 图像兼容 | 有 | 尚未移植 |
| 压缩、单模型详情、自动模型发现 | 有 | 尚未移植 |
| 桌面 UI、Windows 加密存储、隧道托管 | 有 | 沿用正式版；beta 独立运行，未接入 UI |

手动计价始终可使用 usage 的 token 数，价格由用户设定；readUsagePrice 开启后改读配置的费用字段。上游没有费用字段时记录“未提供”，不当作零。缓存输入不重复计费。金额使用十进制有理数，不实现自动充值、货币余额或发票。

精确的边生成边扣 token 仍取决于供应商是否持续报告 usage。beta 通过预留单次输出额度与协议 max-token 字段避免并发透支；终末 usage 核算，缺失或中断保留预留。不能承诺在供应商不报告用量或不遵守输出上限时精确实时计费。

## 同条件进程测试

环境：AMD Ryzen 7 7840H with Radeon 780M Graphics；Windows amd64；Node v24.19.0；go version go1.26.10 windows/amd64。Go exe 大小 8.08 MiB。

使用独立模拟上游、独立 Node 子进程和真实 Go exe。相同调用凭证规模、模型映射、请求内容、响应正文、keep-alive 和并发上限（64）。每个正式场景 3 轮，交替执行先后顺序。JSON 每轮 1200 次；SSE 为 24 个事件，按绝对时间每 10 ms 调度，避免相对定时误差累积；16 并发每轮 192 次，64 并发每轮 256 次。首正文时间是客户端读到第一个响应正文的时间，不是模型端生成首 token 的独立测量。

| 场景 | 实现 | 成功请求/秒 | 请求 P99（ms） | 首个正文 P50（ms） | 采样工作集峰值范围（MiB） |
|---|---|---:|---:|---:|---:|
| 1 key / 8 模型，JSON，16 并发 | node | 4618 | 5.31 | 3.33 | 61.7–63.3 |
| 1 key / 8 模型，JSON，16 并发 | go | 9300 | 3.18 | 1.64 | 20.0–21.7 |
| SSE，16 并发 | node | 66 | 249.69 | 5.96 | 68.0–72.5 |
| SSE，16 并发 | go | 68 | 247.25 | 1.33 | 21.2–22.2 |
| SSE，64 并发 | node | 255 | 255.06 | 14.21 | 87.9–122.9 |
| SSE，64 并发 | go | 267 | 249.10 | 4.05 | 26.9–27.8 |
| 200 keys / 100 模型，JSON，16 并发 | node | 1032 | 23.52 | 14.87 | 75.7–99.8 |
| 200 keys / 100 模型，JSON，16 并发 | go | 9125 | 2.52 | 1.70 | 19.3–21.8 |

表中的吞吐、P99 和首正文值分别取每轮指标的中位数，不是合并样本的 P99。工作集由同一个 PowerShell 观察进程每 200 ms 读取；短 JSON 场景的采样可能漏过瞬时峰值。它包含运行时与进程，不含 Electron UI，也不是全机内存。普通用量和费用功能在压测时均关闭，数据不代表 fsync 或 Redis 计价开启后的性能。

128 并发过载场景，每轮 512 次：两种实现均为 64 次成功、448 次 429，没有把拒绝请求算成成功吞吐。额外连续流式测试：node {"200":1024}，7.71 秒；go {"200":1024}，7.57 秒。它仅为短时重复调用，不是数小时或数天的内存泄漏证明。Go 空闲检查：desktop active=0，buffer_reserved_bytes=0，goroutines=200；large-policy active=0，buffer_reserved_bytes=0，goroutines=58。

本机结果支持“Go beta 的索引路径更快、工作集更小”，不支持“所有语言场景都应重写”。Node 也可通过预编译权限索引优化。SSE 的完整耗时主要受模拟上游发送节奏约束，首正文响应与内存差异比总吞吐更有参考意义。压测运行在正常桌面环境，未固定 CPU 亲和性、未隔离其他软件，三轮并不足以建立统计置信度；不应外推公网、供应商速度或生产容量。

## 验证与工程难度

- Go：28 个顶层测试，含子项共 43 项通过，语句覆盖率 78.2%；go vet、Windows amd64 race 检查通过；go mod verify 通过。
- 现有 Node：npm run check 和全部 58 项测试通过，未修改其运行实现。
- 覆盖客户端断连、慢客户端、事件/输出/内存超限、全局与单 key 拒绝、重复 JSON 字段、别名独立授权与改名、运行中撤权、额度并发竞争与重启恢复、损坏日志、磁盘错误、三种用量格式及价格开关。
- Redis 使用 miniredis 验证版本 CAS、两个客户端共享额度、漏通知后轮询恢复；真实 Redis 的网络分区、持久化丢写与故障转移尚未实测。
- govulncheck v1.9.0：Go 1.26.10 下可触达漏洞为 0；导入包和模块也没有已知漏洞告警，详见 security-scan.txt。构建前已将工具链固定到修复版，并升级 golang.org/x/sys 至 v0.44.0。

实现规则、哈希索引和静态别名难度中等偏低；流式协议边界、取消、内存预算、无重复计费恢复和多节点账本一致性难度较高。完成后者的原型并不等于完成真实故障演练、完整供应商兼容和长期运维。原文的“4–6 周、节省 70%”缺少需求边界与验收依据，不能据此安排生产承诺。

生产替换前应优先补齐现有协议与桌面生命周期兼容，再做真实 Redis 持久化/故障切换演练、跨进程长时间压测、账单对账及监控告警。缓冲预算不是 RSS 硬限制，保守额度可能多扣，日志尚无自动轮转，费用审计不是完整账务数据库。
