# 网络切换后的隧道恢复

之前仅启动一次 cloudflared，发生网络故障后只更新界面状态，由同一个子进程自行重连。代理或虚拟网卡变化可能使进程中已解析的边缘地址、连接和重试状态失效，因此手动停止再启动可以恢复。

现在由卷桥管理隧道子进程的恢复：

- 每 3 秒检查非回环网卡地址和本进程可见的 DNS 服务器列表。变化稳定 4 秒后，停止旧隧道进程并启动新进程，以重新解析边缘地址和建立连接。
- 网络切换没有体现在网卡地址中时，若所有已注册连接持续中断 30 秒，自动重建隧道。重复错误日志不会不断延后这个时限。
- 启动阶段没有建立连接时，固定协议等待 60 秒；自动模式等待 180 秒，为 cloudflared 自身从 QUIC 回退到 HTTP/2 预留时间。参考 [Cloudflare 连接故障说明](https://developers.cloudflare.com/tunnel/troubleshooting/)。
- 子进程意外退出会退避重试，间隔为 1、3、10、30、60 秒，上限 60 秒；持续正常连接 60 秒后重置退避。
- 尚有健康连接或只是本地上游服务报错时，不因单条隧道错误日志重建。已经自行恢复的连接会取消尚未执行的恢复任务。
- 每次确认旧进程退出后才启动新进程，忽略旧进程的迟到输出。手动停止、退出应用时取消网络检查和所有待执行重试，避免再次拉起隧道。
- 无效令牌和无法启动可执行文件等错误会停止自动重试并显示错误。

自动恢复只替换 cloudflared，不重启 Go 网关，不重置密钥、请求计数或请求记录，不写入配置。重建时正在经过旧隧道的公网请求可能中断，客户端需要重试。

验证包含确定性计时器测试，以及隔离配置下的 Electron、真实隧道替身子进程和真实 Go 网关集成测试：模拟网络来回切换，检查隧道 PID 替换、网关 PID 不变、请求记录保留、配置文件不变，以及手动停止后不再启动进程。测试不切换用户电脑的真实虚拟网卡或代理。
